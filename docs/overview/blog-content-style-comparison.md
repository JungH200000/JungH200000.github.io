- 비교일: 2026-08-07
- 현재 프로젝트 글: `_posts/`
- 구현 블로그 글: `website_blog/src/content/posts/`

후속 적용 문서: [글 상세 페이지 편집형 리디자인 계획](../post-detail/redesign-plan.md)을 우선 검토하며, [홈·아카이브 정보 배치안](../home-archive/blog-home-archive-layout-plan.md)은 이후로 보류한다.

## 1. 비교 범위와 한계

현재 프로젝트에는 166개 글이 있고, `website_blog`에는 공개 글 3개와 초안 템플릿 1개가 있다. 따라서 아래 비교는 두 말뭉치의 완성도나 작성자의 전체 문체를 동등하게 평가하는 자료가 아니다.

- 현재 프로젝트: 여러 달 동안 축적된 TIL, 위클리 페이퍼, 프로젝트 진행 기록과 회고
- `website_blog`: 새 사이트의 작성 규칙을 보여 주는 짧은 시드 콘텐츠와 템플릿

수치는 Markdown 원문을 기준으로 계산했다. 코드 블록·HTML·표가 포함되므로 글자 수와 줄 수는 읽기 분량의 절대 지표가 아니라 형식 차이를 보는 참고값이다.

## 2. 전체 요약

현재 프로젝트의 글은 **과정과 증거를 많이 남기는 작업 기록형**이다. 요구 사항, 질문, 문제 상황, 코드, 스크린샷, 링크가 자세하고 실제 학습·개발 흐름을 복원하기 좋다. 대신 제목·헤딩·HTML 표현이 시리즈마다 다르고 초안 흔적도 함께 남아 있어 편집 규칙은 느슨하다.

`website_blog`의 글은 **독자가 다시 활용할 판단 기준을 짧게 정리하는 편집형**이다. 문제와 맥락, 핵심 원리, 검증, 적용하지 않을 조건, 다음 단계처럼 일정한 질문 순서를 사용한다. 읽기는 쉽지만 현재 샘플만으로는 기존 글의 깊이와 현장 증거를 대신하지 못한다.

가장 적절한 방향은 현재 프로젝트의 기술적 깊이와 증거를 유지하면서 `website_blog`의 메타데이터 규칙과 본문 계층을 적용하는 것이다.

## 4. Front matter 형식 비교

### 4.1 현재 프로젝트

166개 글이 다음 필드를 공통으로 사용한다.

```yaml
title: '[TIL 89일 차] Sprint Mission12'
excerpt: '4.심화 요구사항'
categories:
  - Sprint TIL
tags:
  - [Codeit Sprint, Codeit Sprint TIL]
permalink: /categories/codeit-sprint/sprint-til/sprint-til089
toc: true
toc_sticky: true
date: 2026-06-20
last_modified_at: 2026-06-20
```

특징은 다음과 같다.

- `permalink`를 글마다 직접 관리한다.
- 모든 글에서 목차를 활성화하므로 짧거나 빈 글에도 같은 설정이 들어간다.
- 카테고리·시리즈 정보가 front matter뿐 아니라 제목의 대괄호 접두어에도 반복된다. 166개 중 146개 제목이 `[...]`로 시작한다.
- `excerpt`가 선택적으로 작성되어 목록·검색·공유 설명의 품질이 일정하지 않다.
- `last_modified_at`을 항상 두기 때문에 실제 수정 여부와 최초 작성일의 차이를 표현하기 어렵다.
- Jekyll이 읽을 수는 있지만 저장소 안에서 필드 길이, 허용 값, 카테고리 깊이를 검증하는 스키마는 없다.

### 4.2 `website_blog`

일반 글은 다음 형식을 사용한다.

```yaml
title: "좋은 학습 기록을 만드는 네 가지 질문"
description: "검색 결과와 공유 카드에 사용할 180자 이내의 설명"
publishedAt: 2026-07-14
type: learning
categoryPath: [문서화, 학습법]
tags: [학습법, 문서화, 개발]
draft: false
```

특징은 다음과 같다.

- Astro Content Collection과 Zod가 필수값과 형식을 빌드 시점에 검증한다.
- `description`은 필수이며 180자 이하로 제한된다.
- `type`은 `learning`, `retrospective`, `model-update` 중 하나다.
- `categoryPath`는 최대 2단계이며 각 이름에 `/`를 허용하지 않는다.
- `updatedAt`은 실제 수정일이 있을 때만 선택적으로 추가한다.
- `draft: true`인 글은 공개 목록에서 제외한다.
- 파일명이 글 URL 식별자가 되므로 영문 kebab-case를 권장한다.
- 모델 업데이트 글은 `vendor`, `model`, `announcementDate`, `officialSources`를 추가로 요구한다.

### 4.3 핵심 차이

현재 형식은 **운영 중 쌓인 URL과 시리즈를 직접 통제하기 좋고**, 구현 블로그 형식은 **새 글의 품질과 화면 메타데이터를 자동으로 일정하게 만들기 좋다**. 기존 글을 옮길 때는 front matter 이름만 바꾸는 것이 아니라 제목 접두어, URL, 카테고리 깊이, 수정일 의미를 함께 정리해야 한다.

## 5. 제목과 정보 계층 비교

### 현재 프로젝트

- `[TIL 89일 차]`, `[Sprint 백엔드 고급 프로젝트]`처럼 분류를 제목에 포함한다.
- 본문에서도 `# 오늘의 성취`, `# 프로젝트 요구 사항`, `# GitHub Repository 주소`처럼 H1을 여러 번 사용한다.
- 144개 글이 본문 H1을 사용하고, 118개 글은 H1을 두 개 이상 사용한다.
- 페이지 템플릿이 이미 글 제목을 H1으로 출력하므로 문서 의미 구조에서는 H1이 중복된다.
- 일부 글은 `## 2. 문제`, `## 2. 질문`, `## 2. 고민`처럼 같은 번호를 반복해 진행 중 메모의 성격이 그대로 남아 있다.

### `website_blog`

- 제목은 `개발 기록을 시작하며`, `AI 모델 업데이트를 읽는 기준`처럼 내용 자체만 표현한다.
- 유형·카테고리·태그는 화면의 breadcrumb와 메타데이터가 담당한다.
- 본문은 H2와 H3만 사용하고, 페이지 제목이 유일한 H1이 된다.
- 목차는 H2/H3만 수집하므로 헤딩 수준이 곧 화면 탐색 구조가 된다.

구현 블로그 방식이 접근성·검색엔진·목차 일관성에는 더 적합하다. 다만 기존 제목 접두어는 시리즈를 빠르게 식별하는 장점이 있으므로, 삭제할 경우 반드시 유형·카테고리 표시가 목록과 글 상단에서 충분히 보여야 한다.

## 6. 글 유형별 문체와 구성

### 6.1 현재 프로젝트

#### TIL

`오늘의 성취 → 개발 진행 상황 → 문제/질문/고민 → 프로젝트 요구 사항 → 저장소/보관 코드` 형태가 자주 보인다. 요구 사항 체크리스트와 원문 코드가 길게 포함되어 당시 작업을 재현하기 좋다. 반면 미완성 섹션과 중복 번호도 그대로 노출될 수 있다.

#### 위클리 페이퍼

`Q1 → 답변 → 세부 개념`, `Q2 → 답변`의 문답형 구조다. 개념 비교와 목록 중심 설명에 적합하고 학습 과제의 요구 사항을 따라가기 쉽다.

#### 프로젝트 기록

작업 일지와 문제 해결 글은 오류 상황, 원인 후보, 코드, 스크린샷, 해결 결과를 순서대로 쌓는다. 증거량이 많아 기술적 가치가 높지만 글마다 도입·결론의 밀도가 다르다.

#### 프로젝트 회고

최근의 `MOPL 프로젝트 회고록`처럼 역할, 선택 이유, 문제, 해결, 아쉬움을 1인칭 서술로 연결한 글은 이미 편집형 글에 가깝다. 이런 글은 내용을 줄이기보다 제목·메타데이터와 헤딩 계층만 정리해도 `website_blog` 형식에 잘 맞는다.

### 6.2 `website_blog`

#### 학습

기술 이름을 나열하기보다 `어떤 문제를 해결하는가 → 핵심 원리는 무엇인가 → 직접 어떻게 검증했는가 → 적용하지 않을 조건은 무엇인가`의 질문 순서를 사용한다. 개념, 검증, 선택 비용이 한 글 안에서 연결된다.

#### 회고

맥락과 판단 기준을 먼저 제시하고, 사실과 의견을 구분하며, 실행 가능한 예제와 앞으로의 방향으로 마무리한다. 결과만 보여 주기보다 왜 그렇게 판단했는지를 남기는 문체다.

#### 모델 업데이트

공식 출처 안내, 입력·출력 계약, 도구 사용, 비용·지연, 벤치마크 해석, 도입 전 회귀 평가 순으로 구성한다. 뉴스 요약보다 도입 판단 체크리스트에 가깝다.

### 6.3 문체 차이

| 기준 | 현재 프로젝트 | `website_blog` |
| --- | --- | --- |
| 주된 독자 | 미래의 나, 과제·프로젝트 맥락을 아는 독자 | 배경을 모르는 외부 독자까지 포함 |
| 중심 질문 | 오늘 무엇을 했고 무엇이 문제였는가 | 어떤 판단을 다음에도 재사용할 수 있는가 |
| 정보 전개 | 원자료와 작업 순서를 많이 보존 | 맥락·원리·검증·결론으로 재편집 |
| 문장 단위 | 메모, 체크리스트, 코드, 짧은 설명이 혼합 | 완결된 문단과 제한된 목록 중심 |
| 증거 | 코드와 스크린샷이 풍부함 | 작은 예제와 표·Mermaid를 선별 사용 |
| 마무리 | 링크, 저장소, 보관 코드 또는 당일 정리 | 적용 조건, 다음 단계, 판단 기준 |

## 7. Markdown 표현 비교

### 현재 프로젝트의 강점

- 81개 글에 코드 블록, 56개 글에 이미지가 있어 실제 구현과 오류를 확인하기 쉽다.
- 표, 체크리스트, 외부 링크, 로컬 이미지를 폭넓게 사용한다.
- 약 362개로 추정되는 코드 블록 중 약 323개 시작 fence에 언어가 지정되어 대부분 문법 강조를 받을 수 있다.

### 현재 프로젝트에서 정리할 부분

- 120개 글이 `<br>`, `<div>`, `<img>` 같은 inline HTML을 포함해 원문 가독성과 다른 렌더러로의 이동성이 낮다.
- 약 39개 코드 블록은 시작 fence에 언어가 없어 문법 강조가 일관되지 않다.
- 본문 H1 중복과 깊은 헤딩 계층이 목차를 과도하게 길게 만들 수 있다.
- 빈 `excerpt`, 빈 본문, `Template` 제목은 공개 전 검증 대상이 되어야 한다.

### `website_blog`의 방식

- 본문은 가능한 한 순수 Markdown으로 작성한다.
- Mermaid는 언어 식별자가 `mermaid`인 fenced code block으로, 코드는 해당 언어를 지정한 fence로 작성해 렌더링과 복사 기능을 활용한다.
- 표와 blockquote는 설명을 보조할 때만 사용한다.
- 글 상단의 제목·설명·날짜·태그는 레이아웃이 자동으로 출력하므로 본문에서 반복하지 않는다.

## 8. 형식을 통합할 때의 권장 규칙

이 절은 콘텐츠를 실제로 이전했다는 뜻이 아니라, 두 형식의 장점을 함께 사용할 때의 기준이다.

1. 현재 글의 기술적 사실, 코드, 스크린샷, 문제 해결 과정은 삭제하지 않는다.
2. 제목에서 시리즈 접두어를 분리하고 `type`·`categoryPath`로 옮긴다.
3. 각 글에 검색 결과만 읽어도 내용을 판단할 수 있는 180자 이내 `description`을 작성한다.
4. 페이지 제목만 H1으로 두고 본문은 H2/H3부터 시작한다.
5. TIL은 `목표 → 수행 → 문제와 원인 → 검증 → 다음 단계`처럼 빈 섹션이 생기지 않는 최소 구조로 다듬는다.
6. 프로젝트 글은 `맥락 → 선택 → 구현 → 증거 → 결과/한계` 순서로 재배열한다.
7. 코드 fence에는 언어를 지정하고, 레이아웃 목적의 `<br>`·`<div>`는 Markdown 문단과 목록으로 교체한다.
8. UI·오류 증거는 스크린샷으로 유지하고, 시스템 흐름은 수정이 쉬운 Mermaid로 바꿀 수 있는지 개별 판단한다.
9. `updatedAt`은 실제 공개 후 수정했을 때만 추가하고, 초안은 `draft: true`로 관리한다.
10. 기존 permalink와 새 파일명 URL의 대응표를 만든 뒤 리디렉션 전략이 정해지기 전에는 기존 글을 제거하지 않는다.

| 현재 카테고리 | 권장 `type` | `categoryPath` 예시 | 비고 |
| --- | --- | --- | --- |
| Sprint TIL | `learning` | `[Codeit Sprint, TIL]` | 하루 작업을 재사용 가능한 학습 단위로 편집 |
| Sprint Weekly Paper | `learning` | `[Codeit Sprint, Weekly Paper]` | Q&A 구조 유지 가능 |
| 백엔드 초급/중급/고급 프로젝트 작업 글 | `learning` | `[프로젝트명, 문제 해결]` | 프로젝트 단계보다 글의 실제 주제를 우선할 수도 있음 |
| 프로젝트 회고 | `retrospective` | `[프로젝트명, 회고]` | 역할·결정·결과·아쉬움 중심 |
| Java 기본/OOP | `learning` | `[Java, 기본]` 또는 `[Java, OOP]` | 빈 템플릿은 공개 제외 |
| AI 모델 발표 분석 | `model-update` | `[AI, 모델명]` | 공식 출처 전용 필드 필수 |

`categoryPath`가 최대 2단계이므로 모든 기존 폴더 구조를 그대로 옮기기보다 독자가 찾는 기준으로 재분류해야 한다.

## 10. 최종 판단

현재 프로젝트 글의 핵심 자산은 **양, 기술적 깊이, 실제 증거, 시간 순서**다. `website_blog` 글 형식의 핵심 자산은 **검증되는 메타데이터, 명확한 제목, 일관된 헤딩, 판단 중심의 편집 구조**다.

따라서 새 형식을 적용할 때 목표는 기존 글을 짧게 줄이는 것이 아니다. 원자료를 보존하면서 독자가 `무슨 문제였는지`, `어떻게 검증했는지`, `어떤 조건에서 다시 쓸 수 있는지`를 빠르게 찾도록 구조를 정리하는 것이 적절하다.
