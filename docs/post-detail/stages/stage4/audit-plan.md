# 글 상세 페이지 4단계 전체 글 호환성 조사 계획

- 작성일: 2026-08-10
- 기준 문서: [글 상세 페이지 편집형 리디자인 계획](../../redesign-plan.md)
- 현재 상태: **계획 이행 완료 / 공개 전환 글 158개와 이미지 참조 164개 검증 통과 / 비공개 8개 전환 대상 제외**

## 1. 이번 단계에서 하려는 일

지금까지는 서로 다른 유형의 대표 글 4개에만 `single-editorial`을 적용하고 화면과 공통 기능을 확인했다. 4단계에서는 나머지 글도 새 레이아웃을 사용할 수 있는지 전체적으로 조사한다.

바로 `_config.yml`을 바꾸지는 않는다. 먼저 모든 글을 살펴보고 다음 세 그룹으로 나눈다.

- 바로 적용해볼 수 있는 글
- 실제 화면을 보고 판단해야 하는 글
- 본문을 고치거나 기존 레이아웃을 유지해야 할 가능성이 큰 글

조사가 끝나면 유형별 통계와 글 목록을 문서로 남기고, 어떤 순서로 새 레이아웃을 적용할지 제안한다.

## 2. 이번 조사에서 변경하지 않는 것

이 계획을 작성할 당시에는 분석과 문서 작성까지만 진행했다. 이후 사용자가 일괄 적용과 유형별 전환을 승인해 실제 변경은 [통합 구현 결과](implementation.md)에 기록했다. 계획을 세우는 작업 자체에서는 다음 항목을 변경하지 않았다.

- `_config.yml`의 posts 기본 layout
- `single-editorial` Liquid와 Sass
- 홈·아카이브·카테고리 페이지
- 게시글의 layout, excerpt, 본문과 permalink
- GitHub Pages 배포

조사에서 문제가 보여도 바로 수정하지 않고 파일 이름, 문제와 권장 처리 방법을 먼저 결과 문서에 기록했다. 이후 승인된 배치에서만 layout, heading, 이미지 태그와 permalink를 필요한 범위로 수정했다.

## 3. 먼저 다시 확인할 통계

현재 알고 있는 수치는 다음과 같다.

```text
전체 게시글: 166개

[구조]
- H1 없음: 22
- H1 1개: 26
- H1 2개 이상: 118
- excerpt 있음: 91
- excerpt 없음/비어 있음: 75

[콘텐츠]
- 코드 블록 포함: 83
- 이미지 포함: 61
- 표 포함: 37
- inline HTML 포함: 24

[예상 호환성]
- 🟢 바로 적용 가능: 48
- 🟡 확인 후 적용: 79
- 🔴 콘텐츠 수정 필요: 39
```

이 수치는 아직 확정값으로 사용하지 않는다. 현재 `_posts/`를 다시 조사해 전체 파일 수와 각 항목을 확인한다.

H1과 excerpt 항목은 각각 합계가 전체 글 수와 같아야 한다. 반면 코드, 이미지, 표와 HTML은 한 글에 여러 항목이 함께 있을 수 있으므로 합계가 전체 글 수보다 커질 수 있다.

## 4. 글마다 확인할 내용

| 구분 | 확인 내용 |
| --- | --- |
| 기본 정보 | 파일, 제목, 날짜, 카테고리, permalink, 공개 여부 |
| 레이아웃 설정 | `layout`, `toc`, `sidebar`, `author_profile`, `share`, `comments`, `related` |
| 글 상단 | `excerpt` 또는 `description`, 태그, 수정일, header 이미지·영상 |
| 제목 구조 | H1~H4 개수, 제목 단계가 자연스러운지, 예상 목차 길이 |
| 코드 | 코드 블록 개수, 닫히지 않은 블록, 언어가 없는 블록, 매우 긴 코드 줄 |
| 이미지 | Markdown·HTML 이미지, 로컬 파일 존재 여부, 고정 너비 |
| 표 | Markdown·HTML 표, 열이 많거나 내용이 긴 표 |
| HTML | `<br>`, `<div>`, inline style, iframe, script와 외부 embed |
| 최종 기록 | 호환성 등급, 그렇게 판단한 이유, 권장 처리 방법 |

코드 블록 안에 예제로 작성된 `# 제목`, `<div>` 또는 표 모양 텍스트는 실제 heading이나 HTML, 표로 세지 않는다.

## 5. 호환성은 이렇게 나눈다

### 🟢 바로 적용해볼 수 있는 글

다음 조건을 대체로 만족하는 글이다.

- front matter와 Markdown 구조에 문제가 없음
- 코드 블록이 정상적으로 닫혀 있음
- 이미지와 표를 현재 공통 스타일로 처리할 수 있음
- 고정 너비 iframe이나 복잡한 HTML이 없음
- 기존 `single` 레이아웃의 sidebar나 header 기능에 의존하지 않음

코드, 이미지 또는 표가 있다는 이유만으로 확인 대상으로 올리지는 않는다. 앞선 단계에서 일반적인 코드·이미지·표의 반응형 처리는 이미 확인했다. excerpt가 없을 때는 상단 설명을 생략하고, H1~H3은 현재 목차와 본문 스타일이 지원하므로 이 두 항목도 참고 정보로 따로 기록한다.

### 🟡 화면을 보고 판단해야 하는 글

바로 오류라고 볼 수는 없지만 새 레이아웃에서 직접 확인해야 하는 글이다.

- 목차 대상 heading이 30개를 넘음
- heading 단계가 중간에 건너뜀
- 넓은 표 또는 매우 긴 코드가 있음
- `<div>`나 비표준 태그처럼 별도 화면 확인이 필요한 HTML을 사용함
- header 이미지·영상, sidebar, share 기능을 사용함
- 제목 구조나 permalink가 일반적인 글과 다름

단순 `<br>`, `<span>`, `<img>`, 고정 너비 이미지, 언어 없는 코드 fence는 CSV의 `참고 신호`에 남긴다. 현재 공통 스타일이 처리할 수 있으므로 그 사실만으로 🟡로 올리지는 않는다.

### 🔴 수정하거나 기존 레이아웃을 유지할 가능성이 큰 글

- front matter를 정상적으로 읽을 수 없음
- 코드 블록이나 HTML이 닫히지 않음
- 로컬 이미지 파일이 없음
- 모바일 화면을 밀어낼 수 있는 고정 너비 iframe·table·div가 있음
- script, 복잡한 embed 또는 글 안에서 직접 만든 레이아웃을 사용함
- 기존 `single`의 sidebar·header 구조가 글을 이해하는 데 필요함
- permalink가 다른 글과 겹침

🔴도 분석만으로 “반드시 수정해야 한다”고 확정하지 않는다. 원문과 실제 화면을 확인한 뒤 새 레이아웃 적용, 본문 수정 또는 기존 `single` 유지 중 하나를 선택한다.

한 글에 여러 조건이 있으면 가장 조심해야 하는 등급으로 분류하고, 판단 이유를 함께 적는다.

## 6. 조사 방법

### 6.1 전체 목록 만들기

1. `_posts/` 아래 게시글 파일을 모두 찾는다.
2. front matter를 읽어 제목, 카테고리와 설정을 정리한다.
3. `published: false`, 미래 날짜, Template 글도 먼저 목록에 포함한다.
4. 분석에서 제외할 글이 있다면 이유와 개수를 따로 기록한다.

### 6.2 Markdown과 파일 확인

- heading, 코드 블록, 이미지, 표와 HTML을 글별로 센다.
- 상대 이미지 경로가 실제 파일로 연결되는지 확인한다.
- 코드 fence 안의 예제가 콘텐츠 통계에 포함되지 않게 한다.
- 자동 집계 결과 중 일부를 원문과 직접 비교해 잘못 센 항목이 없는지 확인한다.

### 6.3 결과가 맞는지 확인

다음 숫자가 서로 맞아야 한다.

- 전체 파일 수 = 분석한 글 + 제외한 글 + 읽지 못한 글
- H1 구간별 합계 = 분석한 글 수
- excerpt 있음·없음 합계 = 분석한 글 수
- 🟢·🟡·🔴 합계 = 등급을 정한 글 수

## 7. 조사 결과로 만들 문서

분석 결과는 4단계 패키지 안에서 문서와 데이터로 나눠 관리한다.

```text
docs/post-detail/stages/stage4/
├─ audit-result.md
└─ data/
   └─ post-inventory.csv
```

### 조사 결과 문서

사람이 전체 상황을 이해하고 다음 작업을 결정할 수 있도록 다음 내용을 정리한다.

- 실제 전체 게시글 수
- 구조와 콘텐츠 유형별 통계
- 카테고리·연도별 분포
- 🟢·🟡·🔴 개수와 대표적인 판단 이유
- 여러 위험 요소가 겹치는 글
- 각 등급의 글 목록
- 새 레이아웃 적용 순서
- 기존 `single`을 유지하는 편이 나은 글
- `_config.yml` 변경에 대한 최종 의견

### 글별 CSV

166개 글을 Markdown 표 하나에 모두 넣으면 결과 문서를 읽기 어려워진다. 그래서 각 글의 상세 결과는 CSV로 따로 남겼다.

CSV에는 파일, 제목, 카테고리, 주요 구조, 콘텐츠 유형, 호환성 등급, 판단 이유와 권장 처리를 기록한다.

## 8. 분석이 끝난 뒤의 적용 순서

전체 분석이 끝나도 바로 `_config.yml`을 바꾸지 않는다. 다음 순서로 진행한다.

```text
전체 글 분석과 결과 문서 작성
  ↓
사용자가 분류와 일괄 적용 방식 확인
  ↓
🟢 적용 전 공개 글 132개에 single-editorial 일괄 적용
  ↓
136개 전체 URL의 공통 HTML 검사 준비
  ↓
GitHub Pages에 한 번 배포하고 대표·실패 화면 확인
  ↓
🟡 글은 유형별 대표 글부터 시작해 모든 글을 개별 판단
  ↓
🔴 글은 모두 직접 확인해 수정하거나 기존 single 유지
  ↓
전체 기본 layout 변경 여부 결정
```

🟢 132개는 같은 작업에서 일괄 적용한다. `_config.yml`의 기본값은 건드리지 않고 각 글에 `layout: single-editorial`을 명시하므로 🟡·🔴 글에는 영향이 없다. 변경 파일 목록이 CSV의 대상 목록과 정확히 일치하는지 먼저 검사하고, 132개 변경은 되돌리기 쉬운 하나의 독립된 커밋으로 관리한다.

132개를 모두 사람이 하나씩 확인하는 대신 새로 적용한 132개와 기존 대표 글 4개의 URL을 공통 검사한다. HTTP 응답, 레이아웃 클래스, 제목·본문, 목차 링크를 136개 전체에서 확인한다. 실제 viewport의 가로 넘침, 이미지 로딩, 코드·표 스크롤과 콘솔 오류는 콘텐츠 유형별 대표 글, 경계값이 큰 글과 검사에서 경고가 나온 글에 집중해 확인한다.

공통 HTML 검사는 136개 전체를 대상으로 한다. Playwright 기반 viewport 자동 검사를 사용할 수 없을 때는 콘텐츠 유형별 대표 글과 HTML 검사 실패·경고 글을 사람이 확인한다. 일괄 적용 대상 132개를 일부 표본만 확인하고 완료 처리하지는 않는다.

🟡은 같은 문제가 있는 대표 글로 먼저 검증 방법을 정하되, 대표 글만 확인하고 끝내지 않는다. 나머지 🟡 글도 모두 원문과 화면을 확인해 새 레이아웃 적용, 본문 수정, 기존 `single` 유지 중 하나로 정리한다. 🔴도 모든 글을 직접 확인한다.

글별 CSV에는 다음 중 하나의 상태를 기록한다.

- 분석 완료·적용 전
- 새 레이아웃 배포 검증 완료
- 기존 `single` 유지
- 콘텐츠 수정 후 재검증 필요
- 보류

기본 layout 변경을 검토할 때는 처리 상태가 비어 있는 글이 없어야 한다.

## 9. `_config.yml`은 언제 바꾸는가

`_config.yml`의 기본 layout은 🟢 일괄 적용과 🟡·🔴 처리까지 끝난 뒤에 결정한다.

다음 중 하나가 준비돼야 기본값을 바꿀 수 있다.

### 모든 기존 글이 새 레이아웃을 사용할 수 있는 경우

유형별 적용과 검증이 모두 끝나고 기존 글에 남은 문제가 없다면 posts 기본 layout을 `single-editorial`로 변경한다.

### 일부 글이 기존 레이아웃을 유지해야 하는 경우

예외 글에 `layout: single`을 직접 지정해 새 기본값의 영향을 받지 않게 한 뒤, 나머지 글의 기본값을 `single-editorial`로 변경할 수 있다.

### 확인이 필요한 글이 많이 남은 경우

기본값은 계속 `single`로 유지한다. 검증이 끝난 글에만 `layout: single-editorial`을 직접 지정하는 선택 적용 방식을 계속 사용한다.

따라서 “모든 글이 무조건 새 레이아웃을 사용해야만 `_config.yml`을 바꿀 수 있다”는 뜻은 아니다. 다만 166개 모든 글이 `새 레이아웃 검증 완료`, `기존 single 유지` 또는 `공개·전환 대상 제외` 중 하나로 정리돼 있어야 한다. 처리 방법을 정하지 못한 글이 남아 있다면 기본값을 변경하지 않는다.

기본값을 변경한 뒤에는 전체 사이트를 빌드하고 모든 게시글 URL을 대상으로 페이지 생성 여부, 제목, 본문, 이미지 경로와 가로 넘침 같은 공통 검사를 수행한다. 여기에 카테고리·연도·콘텐츠 유형별 화면 검토를 추가하고 검색, 이전·다음 글, 관련 글, 댓글과 기존 permalink도 다시 확인한다.

## 10. 진행을 멈추고 다시 상의할 상황

다음 상황에서는 기준을 임의로 바꾸거나 글을 고치지 않고 조사 결과를 먼저 공유한다.

- 실제 전체 글 수가 예상과 크게 다름
- front matter나 Markdown을 읽지 못하는 글이 많음
- 자동 집계 결과와 원문이 자주 다름
- 대부분 글이 한 등급에 몰려 현재 기준이 의미가 없음
- 깨진 이미지나 permalink 중복이 많이 발견됨
- 조사를 계속하려면 게시글이나 레이아웃 수정이 필요함

실제 첫 집계에서는 단순 HTML과 본문 H1을 모두 🟡로 보아 161개가 한 등급에 몰렸다. 이에 게시글을 수정하지 않고 현재 `single-editorial`의 목차·코드·표·이미지 처리 범위를 다시 확인했다. 그 결과 단순 HTML과 H1·excerpt 여부는 참고 신호로 분리하고, 긴 목차·heading 단계·긴 코드·넓은 표·비표준 HTML처럼 실제 화면 부담이 있는 항목만 🟡로 유지했다. 보정 과정과 최종 기준은 [조사 결과](audit-result.md)에 기록했다.
